  - **Follow-up security audit + fixes (same session), four specific areas, findings reported before any change was made:**
    1. **Confidence comparison bug, fixed.** `patterns.py` hardcoded `score=1.0` on every regex match so it could be compared against Presidio's real NLP confidence in `merge.py`'s overlap resolution — this "worked" only because 1.0 happens to be the ceiling. Reproduced a genuine tie: Presidio's own built-in `CREDIT_CARD` recognizer also returns `score=1.0` for a real card number, so a regex-vs-Presidio overlap on a card fell through to an arbitrary width/position tiebreak instead of a documented rule. Fixed by giving `Span` an explicit `source` field (`"presidio"` | `"regex"`) and rewriting `merge_spans` around a documented, non-numeric rule: a regex-layer match on `REGEX_EXACT_FORMAT_ENTITIES` (`API_KEY`, `CREDIT_CARD`) always wins over an overlapping Presidio span, full stop, regardless of score; everything else still falls back to comparing Presidio's genuine scores (like-with-like). 4 new tests in `test_merge.py` prove the rule directly, including the exact tie scenario found during the audit and a case where Presidio's score is *higher* than the regex layer's (proving it's a source-based rule, not a lucky tiebreak).
    2. **Fernet key startup-leak, fixed; rotation documented as a known limitation.** Grepped the whole codebase for `REDACTION_VAULT_KEY` — never logged/printed/hardcoded anywhere in application code. But reproduced a real leak: pydantic's `ValidationError` embeds the *entire* raw input dict (including every other correctly-configured secret in plaintext) into its message whenever any *one* required setting is missing — confirmed `SecretStr` does not prevent this, since the leaked dict is pre-validation raw input, not the validated field. We'd already hit a live instance of this exact bug class in a previous session's Docker logs. Fixed in `app/config.py`: `_load_settings()` now catches `ValidationError`, extracts only offending field *names* (`err["loc"]`, never `err["input"]`), and raises a sanitized `RuntimeError` — critically, raised *outside* the `except` block (not via `raise ... from None` inside it), because Python auto-attaches the currently-handled exception to a new exception's `__context__` regardless of the `from` clause; `from None` only suppresses *display* of that, it doesn't clear it. New regression test (`test_load_settings_error_never_leaks_a_sibling_secret_value`) sets a distinctive secret value and asserts it's absent from the raised error's message, `__cause__`, and `__context__`. Also added an explicit "no key rotation" limitation comment directly on the `REDACTION_VAULT_KEY` field.
    3. **Raw-PII-on-crash, contained.** Fuzzed `analyze_text()` with NUL bytes, control chars, a lone UTF-16 surrogate, and a ~100K-char input. Found one reliable crash: a lone surrogate character makes spaCy's tokenizer raise `UnicodeEncodeError` (confirmed via full traceback down into `spacy/strings.pyx: hash_string`). Checked its actual content — spaCy hashes per-token, so the exception's `.object` was only the single bad character, not the surrounding email/card in the test text — but that's an accident of spaCy's internals, not something our code enforces, and the shared pipeline runner (`app/core/pipeline.py`) logs any stage's exception via bare `repr(exc)` with no awareness that this stage's content is sensitive. New regression test uses the actual reproducible surrogate-character crash (not a mock), with `caplog`, asserting neither the raised exception nor anything logged contains the email/card used in the test input.

  - **Design decisions that deviate from or extend the module plan (all documented in the code):**
    1. The stage runs **after `pii_redaction_stage`**, not straight after threat detection: the PII count is a feature, and everything stored or re-scanned (review excerpt, redact re-scan) is then post-redaction, so raw PII never reaches the review queue. Threat detection never blocks, so this costs nothing.
    2. **Reward table adjusted from the first draft** (redact on attack 0.0 instead of −0.5; escalate −0.1 / +0.45 instead of −0.2 / +0.4): the draft made redact and escalate never optimal at any attack probability (two dead arms). Final bands under calibrated scores: allow < 0.33 < redact < 0.57 < escalate < 0.80 < block. `test_reward.py` pins both the table and the bands.
    3. **Warm-start prior:** each arm is seeded with pseudo-observations of its expected reward if the classifier were calibrated (~50 observations' worth), so day one behaves like the reward bands rather than random exploration. The prior doesn't count in `update_counts`.
    4. **Safety mask:** `allow` is never selectable at attack probability ≥ `BANDIT_ALLOW_MASK_THRESHOLD` (0.99), whatever was learned.
    5. **Extra feedback sources** beyond escalations: a `BANDIT_SPOT_CHECK_RATE` (2%) random sample of other decisions goes to the review queue (otherwise allow/block never get labels); and a system-prompt leak caught by `output_scan` after an allowed request is an automatic attack label (`reward_source="output_scan"`). Only the taken action is updated (true bandit feedback). Each event is learned from at most once.
    6. **redact_and_allow** re-scans the post-redaction conversation (not system messages), cuts windows at ≥ min(0.5, top window score) so the window that drove the decision is always removed, and also cuts any text past the classifier's 32-window cap (never scanned, so never passed). Failures re-raise a type-name-only `DefenseError` (no request text in logs).
    7. NaN/inf threat scores raise instead of being clamped: Python's `max(0.0, nan)` is `0.0`, which would have read a NaN score as "benign" (fail-open). Found while writing `features.py`; regression-tested.
